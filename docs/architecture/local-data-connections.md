# Where personal data comes from, and how to connect

**Mycelium gets personal records from its desktop UI and explicit imports in Settings → Data.** The one-way importer reads selected Notion pages, databases or data sources, and mapped CSV/JSON files into Notes. It does not collect operating-system activity or automatically synchronize Notion. An Obsidian vault importer is not implemented.

## Current raw data sources

| Source | What becomes data | Write path / storage |
|---|---|---|
| Settings → Data: explicit import | Selected Notion content/properties or mapped CSV/JSON records become Notes; relations remain IDs in text | [Import service](../../O_neash%20Dash/src/lib/imports/index.ts) → `notes`, `import_sources`, `import_records`, `import_runs` in the same SQLite file |
| Settings → Personal | Profile/avatar, weekly availability, focus/break preferences and feature choices | [personalSettingsDb](../../O_neash%20Dash/src/lib/personalSettingsDb.ts) → `personal_settings` and append-only `personal_settings_history`; weather location stays in `localStorage` |
| Planner forms and completion actions | Arcs, projects, tasks, estimates, schedules, completion times | [plannerDb](../../O_neash%20Dash/src/plugins/PlannerPlugin/lib/plannerDb.ts) → `arcs`, `projects`, `nodes` |
| Start/pause/finish session controls | Session timestamps, pauses and recorded task effort | [onTheClockDb](../../O_neash%20Dash/src/plugins/PlannerPlugin/lib/onTheClockDb.ts) → `work_sessions`, `session_nodes`, `session_pauses` |
| Routine configuration | Templates/rules entered by you; generated task/event occurrences | [routineDb](../../O_neash%20Dash/src/plugins/PlannerPlugin/lib/routineDb.ts) → routine tables and planner records |
| Notes editor and comments | Typed/pasted content, selected images, wiki links; derived backlinks and title aliases | [notesDb](../../O_neash%20Dash/src/plugins/NotesPlugin/lib/notesDb.ts) → `notes`, `note_links`, `note_title_aliases`, `doc_comments`; image files alongside SQLite |
| Sleep, habit and journal UI | Logged sleep/wake times, targets, habit checks and journal entries | [sleepDb](../../O_neash%20Dash/src/plugins/SleepTrackerPlugin/lib/sleepDb.ts), [habitsDb](../../O_neash%20Dash/src/plugins/HabitsPlugin/lib/habitsDb.ts), [journalDb](../../O_neash%20Dash/src/plugins/JournalPlugin/lib/journalDb.ts) → personal tracking tables |
| Academic, dispatch, wardrobe and film UI | Entered schedules, placements, catalog details and selected media | [Domain diagram gallery](previews.md) → domain tables and media files |
| External news/research/weather/quote services | Display content fetched from remote services | Widget state, memory cache or `localStorage`; these are not imports into personal task/note/sleep history |

Analytics reads and joins these existing records. It does not create a separate raw-data source. IDs, timestamps and some derived records are generated by application code or SQLite. A development dummy-data utility also exists in `plannerDb`; dummy records are not imported personal history. Legacy [noteSearch](../../O_neash%20Dash/src/plugins/PlannerPlugin/lib/noteSearch.ts) reads an old app-specific JSON layout, has no active callers, and is not an Obsidian importer.

## Run the supported local application

**No database server is required.** The native process opens one SQLite file through [initialization](../../O_neash%20Dash/src-tauri/src/database/mod.rs); [TypeScript DB helpers](../../O_neash%20Dash/src/lib/db.ts) reach it through Tauri SQL/native IPC. There is no localhost SQL HTTP API or browser-only database implementation.

Windows development requires Node (this workspace uses 24.18.0), pnpm 11.19.0, Rust/Cargo with the MSVC toolchain, Microsoft C++ Build Tools/Windows SDK and WebView2. This ARM64 setup also uses Clang. See [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) and the [verified project checkpoint](../project-status.md).

From the repository root in PowerShell:

```powershell
Set-Location '.\O_neash Dash'
pnpm install --frozen-lockfile
pnpm tauri dev
```

Installation is needed for a fresh checkout or changed dependencies. `pnpm tauri dev` automatically starts Vite at `http://localhost:1420` and launches the native window, as defined by [Tauri configuration](../../O_neash%20Dash/src-tauri/tauri.conf.json). Do not start a second Vite process on that port. Opening that address in an ordinary browser does not provide native database access. Close the app and stop the development command with Ctrl+C when finished. Packaged release builds do not need the Vite server.

| Environment | Native-selected database |
|---|---|
| Development/debug | `Documents/O-neash-data-dev/oneash-DB.db` |
| Packaged release | `Documents/O-neash-data/oneash-DB.db` |

`Documents` means the OS-resolved Documents directory, which can be redirected. The native function above is authoritative; the `sqlite:test.db` configuration entry is not the personal domain database.

## Connection methods

| Method | Requirements and present status |
|---|---|
| Inspect existing SQLite on desktop | Open a **snapshot copy** in [DB Browser for SQLite](https://sqlitebrowser.org/) or [DBeaver's SQLite connection](https://dbeaver.com/docs/dbeaver/Database-driver-SQLite/). Choose SQLite and the file, not a server hostname. Prefer read-only access; [DBeaver supports a read-only connection setting](https://dbeaver.com/docs/dbeaver/Managing-security-restrictions-for-database-connection/). Neither tool was installed by this work. |
| Browse/export tabular data | **Settings → Data** provides read-only, paginated table inspection and whole-table CSV/JSON export to a chosen local folder. [Native browser/export code](../../O_neash%20Dash/src-tauri/src/data_management/browse.rs) uses an explicit table allowlist. Notes PDF export remains a separate macOS-only document feature. |
| Import CSV/JSON | **Settings → Data → Import into Notes** accepts files up to 10 MiB and at most 500 records per batch. Map stable ID, title and text-content fields, keep the source label consistent, preview, then explicitly import. Arbitrary SQLite database merging is not implemented. |
| Import Notion | Share a page/database/data source with the Notion connection, enter its token and source URL/ID, choose its type and a limit of 1–100, then preview. The token stays in memory and clears after preview success, cancellation or leaving the section. Nothing is fetched at startup. Explicit Import rechecks local changes; this does not write back to Notion. |
| Import an Obsidian vault | **Proposed, not implemented.** Read Markdown/frontmatter and attachments from a selected vault; map files, wiki links and media into Notes records. No extra database server is needed. |
| Let other local apps query Mycelium over HTTP | **Proposed, not implemented.** Add an explicit localhost API and access policy, initially read-only, over the same SQLite file. Define ownership of writes/migrations before enabling mutations. There is currently no API launch command. |
| Use PostgreSQL or another external database | **Future architecture change.** Requires a database service, connection configuration, backend/driver integration, SQL/schema adaptation and migration/sync design. It is not enabled by changing the current SQLite URL. |

The importer stores source identity, external record IDs and a baseline content hash. Unchanged records are skipped; locally edited, archived or deleted notes are preserved. A fresh check precedes the transaction, and completed-run counts commit with the notes. It does not map imported records to planner tasks or download media. See the [import flow](15-import-flow.svg), [provenance tables](14-import-provenance.svg), and [customization map](customization-map.md).

## Backup, restore and inspection copies

Use **Settings → Data → Backup** to create a new local backup folder. The app flushes pending notes, blocks overlapping UI edits, drains its SQLite pool, snapshots the database with `VACUUM INTO`, copies the four media directories, and writes a manifest with checksums and allowlisted WebView preferences. The pool reopens even when backup fails. A backup is accepted only after manifest, database and media-reference validation. [Backup implementation](../../O_neash%20Dash/src-tauri/src/data_management/backup.rs), [pool handling](../../O_neash%20Dash/src-tauri/src/data_management/mod.rs).

Restore validates the chosen backup, copies and migrates a staged version, relinks managed media paths, and requires restart. Native startup applies the staged folder before opening SQLite and retains the original data folder for rollback. The app then applies the allowlisted WebView preferences. Canceling before restore starts retains the staged copy rather than deleting it. Invalid checksums, missing media, incompatible schema or broken foreign-key links are rejected; no automatic data repair is attempted. [Restore flow](16-backup-restore.svg), [native restore](../../O_neash%20Dash/src-tauri/src/data_management/restore.rs).

For manual inspection, use the database inside a validated backup copy. Alternatively close Mycelium and other writers completely and copy the whole environment data directory. A manual folder copy contains the four media directories but not WebView preferences; use the app backup to include those supported preferences.

For other live-database tooling, SQLite's [online backup API or `VACUUM INTO`](https://www.sqlite.org/backup.html) provides a consistent database snapshot. If WAL sidecars are present, copying only the main `.db` while it is active can omit committed changes; do not discard the `-wal` file. See [SQLite's WAL documentation](https://www.sqlite.org/wal.html). This repository does not explicitly select WAL mode. External database/file editors are outside Mycelium's maintenance gate; close those writers during backup. A database-only snapshot does not include media or WebView preferences.

No personal database, image directory, credentials or machine-specific connection configuration belongs in the GitHub architecture artifacts.
